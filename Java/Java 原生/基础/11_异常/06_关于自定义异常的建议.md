# 自定义异常的建议

以下内容的建议不仅包含 Java 官方的建议，也包含作者本人的建议，可以采取也可以不采取。

## 异常设计的初心

通过区分检查和未检查异常，平衡 “明确错误责任” 与 “代码清晰度”。检查异常强制开发者暴露可恢复的风险，未检查异常则聚焦于无法恢复的编程错误，两者的选择应基于 “客户端是否能合理恢复” 这一标准，而非图开发便利。

## 关于异常使用

`RuntimeException`、`Error`及其子类（如`NullPointerException`、`ArithmeticException`等），Java 不强制要求方法通过`throws`声明或用`try-catch`捕获这些异常。

由于 Java 允许可以不去显示处理异常，开发者可以 “滥用” 这一特性，比如：不去声明（throws）方法抛出的异常，或者图省事（表示原本可以预测的异常但不愿去思考等等）直接抛出 `RuntimeException` ，这就导致了后续的开发者或者维护人员并不知道该方法抛出的具体异常信息是什么。

## 总结

### **为何强制声明检查异常？**

- **异常是方法接口的一部分**：方法可能抛出的异常与它的参数、返回值一样，是 “公共编程接口” 的核心组成。调用者必须知道这些异常，才能决定如何处理（比如重试、降级、提示用户等）。
  例如，一个读取文件的方法若可能抛出`IOException`（检查异常），调用者需要知道并处理（如提示 “文件不存在”），否则程序可能崩溃。

### 为何不强制声明未检查异常？

- **未检查异常的本质**：通常由**编程错误**导致（如空指针、数组越界、除以零），这类错误是开发者的失误，而非程序运行中的 “预期风险”。
- **无法合理恢复**：客户端（调用者）无法从这类异常中恢复 —— 例如，`NullPointerException`意味着代码中存在未初始化的对象引用，调用者无法通过逻辑处理修复，只能修改代码。
- **避免代码冗余**：未检查异常可能在程序中频繁出现（几乎任何方法都可能因编程错误抛出`NullPointerException`）。若强制在每个方法声明中添加这些异常，会严重降低代码的清晰度。

### 未检查异常的合理使用场景

- 主要用于表示**用户错误调用方法**的情况。例如：方法要求参数非空，若调用者传入`null`，方法可抛出`NullPointerException`（未检查异常），因为这是调用者的编程失误。

### 核心使用准则

- **检查异常**：若异常发生后，客户端（调用者）能通过合理逻辑恢复（如重试操作、切换数据源、提示用户修正输入），则定义为检查异常（继承`Exception`）。
- **未检查异常**：若异常是编程错误导致，客户端无法恢复（只能通过修改代码解决），则定义为未检查异常（继承`RuntimeException`）。
