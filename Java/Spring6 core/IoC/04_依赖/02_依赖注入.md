# 依赖注入

在前面我们已经了解过，依赖注入，也就是DI，为了实现DI，我们有两种主要的变体，如下：

- 基于构造器依赖注入
- 基于setter依赖注入

## 一、基于构造器依赖注入

首先，先来一个类，当然要基于构造器来进行依赖注入，所以肯定有有参构造函数。

```java
package Dong.Study;

public class ExampleClass {
    
    private int id;
    private String name;
    // 有参构造函数
    public ExampleClass(int id, String name) {
        this.id = id;
        this.name = name;
    }
    
    public void setId(int id) {
        this.id = id;
    }
    
    public void setName(String name) {
        this.name = name;
    }
    
}
```

然后，XML文件配置元数据。

这里配置元数据，有很多细节，一个一个来。

```xml
<!-- 有参构造函数，参数类型匹配 -->
<!-- 使用type属性来指定参数类型，value属性来赋值 -->
<!-- 这里注意 String 的填写，在开发填写时都以 java.lang.String 格式为标准进行书写（有些类不用比如：int，但是除了int，我也不知道还有那些类写法和int一样） -->
<!-- 这里如果有多个相同类型参数，会报错 -->
<bean id="exampleBean_1" class="Dong.Study.ExampleClass">
    <constructor-arg type="int" value="7500000"/>
    <constructor-arg type="java.lang.String" value="dong"/>
</bean>

<!-- 有参构造函数，参数索引匹配 -->
<!-- 根据参数的索引来进行匹配，从0开始 -->
<bean id="exampleBean_2" class="Dong.Study.ExampleClass">
    <constructor-arg index="0" value="7500000"/>
    <constructor-arg index="1" value="dong"/>
</bean>


<!-- 有参构造函数，参数名匹配 -->
<bean id="exampleBean_3" class="Dong.Study.ExampleClass">
    <constructor-arg name="id" value="7500000"/>
    <constructor-arg name="name" value="dong"/>
</bean>
```

综上，第一种在编译时可能会有歧义。

指定一个索引还可以解决构造函数有两个相同类型的参数的歧义。

也可以使用构造函数的参数名称来进行消歧。

## 二、基于setter依赖注入

还是使用`ExampleClass`。

XML文件配置元数据。

```xml
<!-- 这里的name属性需要注意，name属性后面所跟的值，并非指的是ExampleClass中的id属性和name属性，而是指的是set方法的方法名，假设我们将setId()改为setDd()，那么我们就不再能这样写了name='id'，会报错找不到set方法，应该写为name='dd'。 -->
<bean id="exampleBean_1" class="Dong.Study.ExampleClass">
    <property name="id" value="7500000">
    <property name="name" value="dong">
</bean>

<bean id="exampleBean_2" class="Dong.Study.ExampleClass">
    <property name="id" value="7500000">
    <property name="name" value="dong">
</bean>
```

综上，我们可知property标签中name属性指定的是set三个字母后的字母，且以小写字母为开头。

## 三、依赖解析的过程

### 依赖解析

容器按如下方式执行 bean 依赖解析。

- ApplicationContext 是用描述所有bean的配置元数据创建和初始化的。配置元数据可以由XML、Java代码或注解来指定。

- 对于每个Bean来说，它的依赖是以属性、构造函数参数或静态工厂方法的参数（如果你用它代替正常的构造函数）的形式表达的。在实际创建Bean时，这些依赖被提供给Bean。

- 每个属性或构造函数参数都是要设置的值的实际定义，或对容器中另一个Bean的引用。

- 每个作为值的属性或构造函数参数都会从其指定格式转换为该属性或构造函数参数的实际类型。默认情况下，Spring 可以将以字符串格式提供的值转换为所有内置类型，如 int、long、String、boolean 等等。

当`ApplicationContext`容器创建时，容器会扫描每个bean的配置。同时那些具有单例作用域（Spring 中 bean 的默认作用域）并被设置为预实例化的Bean被创建。否则，Bean只有在被请求时才会被创建。

当bean被创建好时，其bean图也随之被创建好，即 bean 的依赖关系和它的依赖关系（等等）被创建和分配。

### 依赖解析不匹配

在 Spring 框架中，依赖解析不匹配问题的延迟出现是一个需要特别注意的特性。

详细去看**依赖解析不匹配**文件。



### 补充：循环依赖

> 如果你使用主要的构造函数注入，就有可能产生一个无法解决的循环依赖情况。
>
> 比如说。类A通过构造函数注入需要类B的一个实例，而类B通过构造函数注入需要类A的一个实例。如果你将A类和B类的Bean配置为相互注入，Spring IoC容器会在运行时检测到这种循环引用，并抛出一个 `BeanCurrentlyInCreationException`。
>
> 一个可能的解决方案是编辑一些类的源代码，使其通过setter而不是构造器进行配置。或者，避免构造器注入，只使用setter注入。换句话说，虽然不推荐这样做，但你可以用setter注入来配置循环依赖关系。
>
> 与典型的情况（没有循环依赖关系）不同，Bean A和Bean B之间的循环依赖关系迫使其中一个Bean在被完全初始化之前被注入到另一个Bean中（一个典型的鸡生蛋蛋生鸡的场景）。
