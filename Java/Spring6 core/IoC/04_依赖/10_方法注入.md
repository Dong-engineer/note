# 方法注入

经过上面的学习，开发者应该知道除了懒加载的 Bean 在进行初始化的时候，只有一次依赖注入的机会——容器 `AppclicationContext` 初始化时。

在大多数的应用场景下 Bean 是单例的，即 Bean 在整个容器中只初始化一次，在后续的操作过程中不管是通过 XML 配置、注解注入，还是通过`ApplicationContext`获取该 Bean，得到的都是同一个实例。

如果一个 Bean 对另一个 Bean 产生了依赖，通常意味着一个Bean被设置为另一个Bean的一个属性，在 *depends-on* 一节中讲述过，可以使用 <ref/> 或者 `ref=""` 去引入外部 Bean。

那么问题也就来了，当一个单例 Bean A 里面使用了非单例 Bean B，此时对于 Bean B 来说他能够初始化的机会只有一次，就是 Bean A 初始化的时候容器检测到 Bean A 中含有 Bean B，容器会优先去将 Bean B 初始化，再去初始化 Bean A，将 Bean B 作为依赖注入到 Bean A中。

这违背 Bean A 和 Bean B 之间的逻辑关系，因为在 Bean A 中去调用 Bean B，永远都只是调用了 Bean B 的最初那个实例。

如下代码示例：

```java
import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;
import java.time.LocalDateTime;

// 声明为prototype（非单例），每次获取都应创建新实例
@Component
@Scope("prototype")
public class OrderLogger {
    private LocalDateTime createTime; // 记录实例创建时间（用于验证是否为新实例）

    // 构造方法：实例化时记录当前时间
    public OrderLogger() {
        this.createTime = LocalDateTime.now();
        System.out.println("OrderLogger实例创建，时间：" + createTime);
    }

    // 记录订单日志的方法
    public void logOrder(String orderId) {
        System.out.println("订单[" + orderId + "]日志记录，使用的实例创建时间：" + createTime);
    }
}
```

```java
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

// 默认单例（@Service注解默认scope为singleton）
@Service
public class UserService {
    // 依赖注入非单例Bean B
    @Autowired
    private OrderLogger orderLogger;

    // 处理订单的方法（每次调用都希望使用新的OrderLogger实例）
    public void processOrder(String orderId) {
        System.out.println("开始处理订单：" + orderId);
        orderLogger.logOrder(orderId); // 调用Bean B的方法
    }
}
```

```java
// 测试代码
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.ComponentScan;

@ComponentScan // 扫描并创建Bean
public class Main {
    public static void main(String[] args) throws InterruptedException {
        AnnotationConfigApplicationContext context = new AnnotationConfigApplicationContext(Main.class);
        UserService userService = context.getBean(UserService.class);

        // 第一次调用processOrder方法
        userService.processOrder("ORD001");

        // 等待2秒，模拟时间间隔
        Thread.sleep(2000);

        // 第二次调用processOrder方法（期望使用新的OrderLogger实例）
        userService.processOrder("ORD002");
    }
}
```

```plaintext
订单[ORD001]日志记录，使用的实例创建时间：2023-10-01T10:00:00.123

订单[ORD002]日志记录，使用的实例创建时间：2023-10-01T10:00:00.123
```

Spring 提出为了解决这个问题，可以牺牲一些 IoC 控制反转，以达到动态获取 Bean B 实例的目的。

## 实现 `ApplicationContextAware` 接口 

```java
import org.springframework.stereotype.Component;

// 非单例Bean
public class OrderProcessor {
    private String orderId;

    public void setOrderId(String orderId) {
        this.orderId = orderId;
    }

    public String process() {
        return "Processing order: " + orderId;
    }
}
```

```java
import org.springframework.stereotype.Service;

// 单例Bean
public abstract class ShoppingCartService implements ApplicationContextAware{
    
    private ApplicationContext applicationContext;

    public String checkout(String orderId) {
        // 每次调用时获取新的OrderProcessor实例
        OrderProcessor processor = createOrderProcessor();
        processor.setOrderId(orderId);
        return processor.process();
    }
    
    public OrderProcessor createOrderProcessor() {
        return this.applicationContext.getBean("orderProcessor", OrderProcessor.class)
    }

    public void setApplicationContext(
            ApplicationContext applicationContext) throws BeansException {
        this.applicationContext = applicationContext;
    }
}
```

```xml
<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="http://www.springframework.org/schema/beans
                           http://www.springframework.org/schema/beans/spring-beans.xsd">

    <!-- 定义ShoppingCartService Bean -->
    <bean id="shoppingCartService" class="XXX.ShoppingCartService"/>

    <!-- 定义OrderProcessor Bean，设置为prototype(非单例Bean)作用域 -->
    <bean id="orderProcessor" class="XXX.OrderProcessor" scope="prototype"/>
</beans>
```

```java
import org.springframework.context.ApplicationContext;
import org.springframework.context.support.ClassPathXmlApplicationContext;

public class MethodInjectionTest {
    public static void main(String[] args) {
        // 加载Spring配置文件
        ApplicationContext context = new ClassPathXmlApplicationContext("applicationContext.xml");
        
        // 获取ShoppingCartService Bean
        ShoppingCartService cartService = context.getBean("shoppingCartService", ShoppingCartService.class);
        
        // 第一次调用checkout方法
        String result1 = cartService.checkout("ORD123");
        System.out.println(result1);
        
        // 第二次调用checkout方法
        String result2 = cartService.checkout("ORD456");
        System.out.println(result2);
        
        // 验证两次获取的OrderProcessor是否为不同实例
        OrderProcessor processor1 = cartService.createOrderProcessor();
        OrderProcessor processor2 = cartService.createOrderProcessor();
        
        System.out.println("processor1和processor2是否为同一实例: " + (processor1 == processor2));
    }
}
```

```cmd
Processing order: ORD123
Processing order: ORD456
processor1和processor2是否为同一实例: false
```

仔细阅读其实可以发现，**在以上代码中牺牲了 `OrderProcessor` 的控制反转，在进行依赖注入的时候需要手动去注入**，如下代码：

```java
 // 每次调用时获取新的OrderProcessor实例        
 OrderProcessor processor = createOrderProcessor();        
 processor.setOrderId(orderId);
```

**但是 Spring 并不提倡让类去实现 `ApplicationcontextAware` ，如果这样做会于 Spring 源码非常强的耦合度，一旦 `ApplicationcontextAware` 进行了更新修改，那么很有可能导致程序无法正常运行。**

Spring 提供了其他方法。

## CGLIB 字节码增强技术

除了实现 `ApplicationContextAware` ，其余的技术是基于CGLIB 字节码增强技术的基础上去实现的。

即在运行时通过字节码技术实现动态生成子类以达到重写的目的。

为什么这么说呢？

在 `ApplicationContextAware` 的代码片段中：

```java
public void setApplicationContext(
        ApplicationContext applicationContext) throws BeansException {
    this.applicationContext = applicationContext;
}
```

通过在运行时实例化单例 Bean 的时候将容器作为依赖手动注入进去，在通过容器动态获取非单例 Bean。所以通过CGLIB 字节码增强技术也是通过这种方式达到动态获取Bean的目的。

于是 Spring 使用**CGLIB字节码增强技术在运行时动态生成一个开发者定义类的子类，通过子类重写父类里面的方法，实现方法注入**。

Spring 规定了被注入的方法书写的规范，如下：

- 需要注入的方法及其类不能是 `final`，因为 `final` 是常量不可以重写（对应上文 Java 语言的限制）。
- 对一个包含 `abstract` 方法的类进行单元测试，需要你自己对这个类进行子类化，并提供一个 `abstract` 方法的 stub 实现。
- 查找方法对工厂方法不起作用，特别是对配置类中的 @Bean 方法不起作用，因为**工厂方法创建的 bean 实例，其生命周期不由 Spring 完全控制**（方法注入（`@Lookup`或 XML lookup）依赖 Spring 在**实例化阶段**生成动态子类（CGLIB），若实例由工厂方法创建，Spring 无法介入实例化过程生成子类，因此查找方法无效。）。

## 基于XML的方法注入

假设开发者有类 `singletonBean`，如下：

```java
public abstract class SingletonBean {
    
    public abstract PrototypeBean getPrototypeBean();
    
}
```

```xml
<bean id="singletonBean" class="com.example.SingletonBean">
    <!-- 方法注入的语法 -->
    <lookup-method name="getPrototypeBean" bean="prototypeBean"/>
</bean>
```

通过CGLIB重写后得代码，如下：

```java
public class SingletonBean$$EnhancerByCGLIB extends SingletonBean {
    private BeanFactory beanFactory;
    
    @Override
    public PrototypeBean getPrototypeBean() {
        return (PrototypeBean) beanFactory.getBean("prototypeBean");
    }
    
    // 用于设置BeanFactory的方法（由Spring内部调用）
    public void setBeanFactory(BeanFactory factory) {
        // Spring的底层会将生成的子类隐式实现BeanFactoryAware接口，从而接收BeanFactory的注入
        this.beanFactory = factory;
    }
}
```

上面这段代码讲述到隐式实现 `BeanFactory` ，那么就有阅读者疑问——这和 `ApplicationContextAware` 一样有耦合度了吗？

这种疑问是错误的，因为具有耦合度的不是开发者的代码，开发者的代码并未被修改，真正和 Spring 代码有耦合度的是生成的子类代码，不过生成的代码也是 Spring 去管理的，所以开发者无需关心。（而且耦合度不是越低越好，整个系统的各个模块之间总会存在一定的耦合度，因为它们需要相互协作，因此，在开发时应当尝试去降低耦合度，而不是让耦合度理想化为0）。

同时这种动态生成代码方法，使得 Spring 达到了 “非侵入”（侵入——修改开发者原有代码），遵守 OCP 原则。

这也解释了为什么要动态生成子类而不去修改开发者源代码的原因？

## 基于注解的方法注入

基于注解的方法注入就很简单了，一个注解的事。

如下：

```java
public abstract class SingletonBean {
    
	@Lookup
    public abstract PrototypeBean getPrototypeBean();

}
```

通过 CGLIB 动态生成的代码一样不再书写。

## 补充

这里补充一下 Spring 对一个包含 `abstract` 方法的类进行单元测试，需要你自己对这个类进行子类化，并提供一个 `abstract` 方法的 stub 实现。

用上面的代码，如下：

```java
public abstract class SingletonBean {
    
    public abstract PrototypeBean getPrototypeBean();

}
```

```xml
<bean id="singletonBean" class="com.example.SingletonBean">
    <!-- 方法注入的语法 -->
    <lookup-method name="getPrototypeBean" bean="prototypeBean"/>
</bean>
```

现在要做单元测试，做单元测试很简单使用 JUnit 的注解，如下：

```java
public abstract class SingletonBean {
    
    // 错误行为
	@Test
    public abstract PrototypeBean getPrototypeBean();

}
```

因为被 `@Test` 注解的方法是抽象的，没有方法体所以这种行为是错误的。

如果想要做测试，可以使用匿名类，如下：

```java
import org.junit.Test;
import static org.junit.Assert.*;

public class SingletonBeanTest {
    
    @Test
    public void testGetPrototypeBean() {
        // 创建匿名子类实例
        SingletonBean singleton = new SingletonBean() {
            @Override
            public PrototypeBean getPrototypeBean() {
                // 返回 stub 对象
                return new PrototypeBean();
            }
        };
        
        // 执行测试
        PrototypeBean result = singleton.getPrototypeBean();
        assertNotNull(result);
        assertTrue(result instanceof PrototypeBean);
    }
}
```
