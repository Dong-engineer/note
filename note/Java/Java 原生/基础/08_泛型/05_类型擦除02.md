# 类型擦除

泛型带来了很多便利，但如果不去正确使用，也会带来很多的问题。

本节主要讲述开发者在开发时使用泛型很容易发生了问题。

## 可具体化和不可具体化类型

这里的可具体化类型和不可具体化类型并不是指是否能够创建具体的对象。而是指的是在编译后是否能够确定其具体类型。

### 可具体化类型：

- 基本类型（如 `int`、`boolean`）；
- 非泛型类型（如 `String`、`ArrayList` 的原始类型）；
- 无界通配符的泛型调用（如 `List<?>`）。

### 不可具体化类型：

- 带具体参数的泛型类型（如 `List<String>`、`Map<Integer, String>`）；
- 有界通配符的泛型类型（如 `List<? extends Number>`）。

可具体化类型与不可具体化类型的主要区别在于：在编译后（即运行时）是否能保留完整的类型信息。

说白了主要还是泛型经过类型擦除机制后所得代码的缘故。

下面一一说明：

基本数据类型、非泛型类型、无界通配符泛型这些类型在编译后，所有的类都不会发生变化，那么通配符 `?` 怎么会不发生变化呢？通配符本质其实就是 `Object` ， `Object` 的特性就保证了其在运行时几乎不会发生类型转化错误。

而带具体参数的泛型类型和有界通配符的泛型类型在编译时经过类型擦除机制，会擦除其具体的类型参数。即：*`List<String>` 和 `List<Number>` 在运行时都会被擦除为 `List`，JVM 无法区分二者。*

## 堆污染

堆污染，对于小白来说很可能没有听过，但是其实已经学习过了。

当**参数化类型的变量引用了不属于该类型的对象**时，就会发生堆污染。其根源是编译时的**未检查警告（unchecked warnings）**—— 当编译器无法验证泛型操作的正确性（如混合原始类型与参数化类型、未检查的强制转换）时，会发出警告，而忽略警告可能导致堆污染。

如下代码：

```java
List<String> list = new ArrayList(); // 原始类型与参数化类型混合，产生未检查警告
list.add(123); // 编译通过（原始类型允许），但运行时实际存储了 Integer，导致堆污染
String s = list.get(0); // 运行时抛出 ClassCastException
```

这段代码和上一节的 `Node`、 `MyNode` 的示例很相似，就是绕过了编译器的检查，编译后对 `List<String> list` 进行了类型擦除，而且 `list` 本身就是 `List` 类型调用 `add()` 没有问题，问题在于 `list` 调用 `get(0)` 取出的是 `Integer`，即参数化类型的变量（`list`）引用了不属于该类型的对象（`list.get(0)`）。

这也就是为什么在 *01_泛型* 一节中提前告知了开发者在 `MyClass` 一例子中只能存储其泛型参数所声明的类型。

## var args 方法的潜在漏洞

var args 即动态参数，使用 `...` 表示接受多个参数。

在开发中开发者很有可能会这样写代码，如下：

```java
public static <T> void addToList(List<T> listArg, T... elements) {
    for (T x : elements) {
        listArg.add(x);
    }
}
// 演示 varargs 方法的漏洞
public static void faultyMethod(List<String>... l) {
    Object[] objectArray = l; // 合法：List<String>[] 是 Object[] 的子类型
    objectArray[0] = Arrays.asList(42); // 存入 List<Integer>，堆污染发生
    String s = l[0].get(0); // 运行时抛出 ClassCastException（Integer 无法转为 String）
}
```

首先是 **Java 不允许不可具体化类型直接创建数组**，如：`List<String>[] lsits`。

因为在经过类型擦除后会变为：`List[] lsits` ，在运行时很有可能会违背开发者原有逻辑，发生类型转换错误。

其次，对于 `T... elements` 编译后会变为 `T[] elements` ，同时又经过类型擦除机制变为 `Object[] elements` 。

### var args 方法——污染的源头

那么开发者就可以使用这一漏洞来对程序进行 `ClassCastException` ，已知 `addToList()` 接受一个 `List` 类型和一个动态参数（也可以是数组）。

如下，注入漏洞：

```java
List<String> lists_str = new ArrayList<>();
List<Integer> lists_int = new ArrayList<>();

// 声明一个可以存储任何类型的 List 集合
List[] lists = {lists_str, lists_int};
// 用作于参数的 List
List<String> list = new Array<>();

addToList(list, lists_str);
```

以上代码编译通过，但是在实际运行时因为 `list_int` 是 `Integer` ，所以会发生类型转化错误。

所以var args 方法可能不会直接造成堆污染，但会间接造成堆污染从而成为污染源。

### 防止var args 方法造成堆污染

- 若方法内部仅读取可变参数（不修改数组、不存入不匹配类型），用 `@SafeVarargs` 注解声明安全性，明确告知编译器 “此方法不会引发堆污染”，代码如下：（Java 官方表示有可能不太理想）

```java
// 注解的使用在下一章详细介绍
@SuppressWarnings({"unchecked", "varargs"})
```

- 禁止在方法内部将泛型可变参数数组赋值给 `Object[]` 后修改其元素（这是最常见的堆污染诱因，如之前的 `faultyMethod` 示例）。

## 总结

在泛型的使用中，作者总结了以下几点：

1. **严格保持泛型参数一致性**，杜绝原始类型与参数化类型的混合使用，确保编译时无 “未经检查” 警告；
2. **安全使用泛型可变参数**：要么保证实参类型一致并通过 `@SafeVarargs` 声明，要么避免在方法内部修改可变参数数组；
3. **合理使用有界通配符**：利用 `extends` 和 `super` 控制读写权限，增强灵活性的同时减少类型错误。
