# 响应延迟

遇见响应延迟，一些没有遇见过该情况的开发者很有可能会想到多线程爬虫。

这是一个小坑，开发者要注意一下。

## 什么是响应延迟？

响应延迟主要发生在服务器上，具体来说是服务器对同一 `IP` 地址的请求会进行队列处理。

## 为什么不能用多线程

响应延迟，指的是对每个请求都进行了延迟处理，开发者选择多线程爬虫想的可能是，多个线程同时请求这一个网站，以此来爬取不同页面的内容。这是错误的想法。

使用多线程去爬取网页内容，但是每次请求的 `IP` 地址都是同一个，这也就导致多线程爬取时会比正常爬取更加缓慢。

多线程的核心优势是并发处理 “独立任务”，但如果所有线程共享同一个 `IP` ，且服务器对该 `IP` 进行 “单队列限流”（即同一  `IP` 的请求必须串行处理，后一个请求需等待前一个完成），此时多线程会退化为 “串行执行”，甚至因线程切换开销和服务器队列拥堵导致更慢。

下面实例响应延迟 `5s`：

```python
# 目标网站
target_url = "https://ssr4.scrape.center/"
# 请求头
header = {
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/"
                  "537.36 (KHTML, like Gecko) Chrome/142.0.0.0 Safari/537.36 Edg/142.0.0.0"
}

# 测试程序，单个网站请求时间
start_time = time.perf_counter()
response = requests.request("GET", url=target_url, headers=header)
code = response.status_code

if code == 200:
    print(response.text)
else:
    print(f"请求失败，错误代码：{code}")

end_time = time.perf_counter()
print(f"耗时：{end_time - start_time}s")  # 5s-6.5s
```

```python
start_time = time.perf_counter()
# 使用线程池
target_urls = ["https://ssr4.scrape.center/page/1", "https://ssr4.scrape.center/page/2",
               "https://ssr4.scrape.center/page/3", "https://ssr4.scrape.center/page/4"]

header = {
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/"
                  "537.36 (KHTML, like Gecko) Chrome/142.0.0.0 Safari/537.36 Edg/142.0.0.0"
}
MAX_WORKERS = 4

thread_group_one = concurrent.futures.ThreadPoolExecutor(MAX_WORKERS, "Thread_Group-1")


with thread_group_one as executor:
    results = executor.map(spider_ssr4.spider_URL, target_urls, [header]*len(target_urls))


end_time = time.perf_counter()
print(f"耗时：{end_time - start_time}")  # 30s-35s
```

运行结果：上面为 `6s` 左右，而下面的预想结果应该和上面的代码是一样的，但是结果表示并非如愿，并且比起正常一个一个网页爬取还要慢上一些，这就是多线程使用时的一个小坑。

## 怎么解决该问题

**应优先检查网站爬取规则，在允许的前提下，通过多 `IP` / 代理池解决单 `IP` 限流问题”**。

以上内容并非绝对否定了多项程的无用，这要看开发者对目标网站限流策略的理解和应对策略是否合理，合理情况下，多线程依然可以提高工作效率。
